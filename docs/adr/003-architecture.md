# ADR-003: Выбор архитектурного стиля

- **Статус:** Accepted
- **Дата:** 2026-01-17
- **Автор:** Сидоров С.С.

## Контекст

Сервис конвертации файлов имеет две принципиально разные нагрузки:
1. HTTP-слой — короткие быстрые запросы (загрузка, статус).
2. Конвертация — тяжёлые CPU-bound задачи (Pillow, pandas).

Нужна архитектура, которая изолирует эти нагрузки и позволяет
горизонтально масштабировать воркеры независимо от API.

## Рассмотренные альтернативы

1. **Монолит** — всё в одном процессе. Просто, но CPU-задача блокирует API.
2. **Слоистая архитектура** — api / services / repositories / models. Понятна, легко тестируется.
3. **Гексагональная** — порты и адаптеры. Избыточна для MVP.
4. **Микросервисы** — отдельные сервисы на каждый формат. Слишком дорого.
5. **Событийная** — Kafka/RabbitMQ. Overkill на MVP.

## Решение

**Слоистая архитектура + выделенные Celery-воркеры.**

Слои:
- `api.py` — HTTP-роутинг и валидация (FastAPI).
- `converters.py` — чистая логика конвертации (без БД, без HTTP).
- `worker.py` — Celery-задачи, вызывают конвертеры.
- `models.py` / `database.py` — доступ к данным.
- `storage.py` — абстракция хранилища (сейчас локально, потом S3).

## Обоснование

- Разделение CPU-bound и I/O-bound — ключевое требование.
- Слоистая архитектура проще гексагональной, но даёт ту же изоляцию.
- Celery — стандарт де-факто для фоновых задач в Python.
- Легко заменить `storage.py` на S3 без изменения API.

## Последствия

**Плюсы:**
- API не блокируется конвертацией.
- Воркеры масштабируются независимо (`docker compose up --scale worker=4`).
- Конвертеры тестируются без БД и HTTP.

**Минусы:**
- Два типа процессов в деплое (api + worker).
- Нужен брокер (Redis) — ещё один сервис.
